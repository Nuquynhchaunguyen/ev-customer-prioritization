EV Customer Prioritization¶

02. Modeling and prioritization¶

Nu Quynh Chau Nguyen | MSBA265 | Fall 2026

Business question: Which customers should an EV dealership prioritize for contact when its outreach capacity is limited?

This notebook compares three classifiers, chooses one using validation data, and evaluates the selected model on a separate holdout. It saves the exact final preprocessing-and-model pipeline used by the Streamlit application. The application's job is to rank a batch of customer profiles, not to make a guaranteed purchase or revenue forecast.

Reading order: problem and data → fixed splits → candidate models → validation comparison → model selection → holdout evaluation → saved model and app handoff. Run all cells in order to reproduce the results.

1. What the data can and cannot tell us¶

The source is the professor-approved Kaggle competition Predicting Electric Vehicle Purchases. The training file contains 668,665 synthetic profiles, with 13 candidate predictors, an id, and the supplied Will_Buy_EV target. The separate Kaggle test.csv has 286,571 unlabeled profiles; it is not our labeled internal holdout and cannot establish model accuracy.

We map No to 0 and Yes to 1. The target is a supplied dataset label; it is not documented as a verified transaction or a purchase within a known time window. Scores in this project estimate the Yes-label probability in this synthetic dataset. Results do not establish that contacting a person causes a purchase.

Initial EDA already inspected the full labeled dataset. The new split is frozen before model fitting and selection, but this holdout is not a dataset nobody has ever looked at. We will not repeatedly tune models against its results. A genuinely external labeled dataset would be a stronger future test.

3. Freeze training, validation, and holdout groups¶

We use a stratified 70% / 15% / 15% split with random seed 42, so each group keeps a similar Yes-label share. Integer rounding determines the exact row counts. A saved ID-to-split manifest records membership for inspection.

  • Training: learn preprocessing and candidate model parameters.
  • Validation: compare models and select one using the rule stated below.
  • Holdout: evaluate the selected final model after refitting on training plus validation. Do not use this result to choose a different model.

Each group's IDs are disjoint. Stratification uses the labels to balance group composition; the holdout labels do not enter preprocessing or fitting.

A scikit-learn Pipeline carries preprocessing and the classifier together. Categorical inputs use one-hot encoding. Numeric inputs are standardized for Logistic Regression; a tree does not require this scaling. All learned transformations fit only on training rows during candidate comparison. We do not apply SMOTE or class weighting in these initial probability baselines. These are fixed, modest configurations, not an extensive search.

The encoder handles an unseen category without a runtime error during model evaluation. The application applies stricter schema validation and rejects unsupported input categories rather than quietly treating them as known.

4.1 How Logistic Regression learns and why these settings were chosen¶

The fitted pipeline turns each synthetic customer profile into numeric inputs. One-hot encoding represents categories without inventing numeric distances; standardization puts the six numeric predictors on comparable scales. During candidate comparison, both transformations learn from training rows only.

For a profile with transformed features x, Logistic Regression computes a score z = wᵀx + b and converts it to a Yes-label probability using the logistic function. Training adjusts w and b to reduce binary log loss while applying L2 regularization. With no class or sample weights in this experiment, the minimized objective is mean binary log loss plus the L2 penalty ||w||² / (2 × C × n), where n is the number of training rows.

The intercept is excluded from the penalty. The stable implementation handles large scores without directly exponentiating them. The diagnostic figure below reports the mean prediction log loss without the regularization term, so the training and validation curves have the same interpretation. This loss evaluates probability estimates; the project's business selection metric remains Lift@K.

L-BFGS uses loss values, gradients, and an approximation to curvature to update the coefficients. It is a reasonable initial solver for this structured, moderate-dimensional problem. The existing model has already completed a fit; this does not establish that its solver or settings are optimal.

Choice Role and reason for the initial setting
C = 1 A transparent initial L2 regularization setting. Smaller C strengthens shrinkage; this value was fixed before comparison, not selected by a tuning search.
solver = lbfgs Uses gradient and curvature information for a smooth logistic objective. Numeric scaling supports stable optimization.
max_iter = 1000 A generous upper iteration cap, allowing the stopping criterion to finish earlier. It is not a target number of updates.
tol = 0.0001 The estimator's configured stopping tolerance. Exact optimizer termination details are not exposed by the public estimator interface.
Tree max_depth = 6 Limits the complexity of interactions and helps keep the comparison tree understandable. It is not a proven best depth.
Tree min_samples_leaf = 200 Requires substantial support for a terminal group and discourages small, unstable leaves in this large dataset. It is an initial design choice.
Dummy strategy = prior Establishes a label-prevalence benchmark without learning profile-specific differences.

These are three prespecified baselines. A future tuning study would use training and validation, or cross-validation within development data; the existing holdout would not be reused to search for better settings.

Iterations and fit checks. The actual number of optimizer iterations is available after fitting; the cap alone does not tell us how many were used. Dummy and Decision Tree fits have no corresponding L-BFGS iteration count. The fit wrapper treats a convergence warning as a failed fit and records elapsed time, row count, parameters, and actual iterations for new fits. Completion without that warning is recorded directly; a count below the cap does not reveal which exact internal stopping criterion fired.

Sources: Logistic Regression, Decision Tree, and native fit callbacks.

5. Define K and the model-selection rule before reading results¶

K is contact capacity: the number of customer profiles the dealership can contact. We compare 1%, 5%, 10%, and 20% of the evaluation batch, rounded up to a whole profile and capped at its size. The app lets the user choose an actual count instead of a percentage.

Metric Interpretation
Precision@K Yes-labeled profiles in the top K divided by K
Recall@K Yes-labeled profiles in the top K divided by all Yes labels in the evaluation group
Lift@K Precision@K divided by that evaluation group's Yes-label share
ROC-AUC Overall separation of Yes and No scores across thresholds
Average precision Precision-recall summary; useful with an imbalanced target
Brier score Mean squared probability error; lower is better

Our primary selection rule is highest validation Lift@10%, followed by ROC-AUC if lift ties. A fixed simplicity order resolves any remaining tie: Dummy baseline, then Logistic Regression, then Decision Tree. At a fixed K and prevalence, comparing lift is equivalent to comparing precision. The 10% choice is a transparent working capacity assumption; a dealership's real capacity would need confirmation.

The Dummy model emits a constant probability. Tied scores use a fixed, label-independent SHA-256 ordering of seed 42 and ID. This also makes tied tree scores reproducible. We show both realized Dummy results and the expected random-selection baseline: precision = prevalence and lift = 1. Random expectation is not a claim that every realized shortlist has lift 1.

7. Evaluate the final pipeline on the held-out 15%¶

Ranking at contact capacity is the main business evaluation. We also report discrimination, probability error, and conventional classification metrics at a 0.50 score threshold. This threshold is a supplementary diagnostic, not the rule used to choose the top K customers.

A reliability plot compares predicted probabilities with observed Yes-label shares in quantile bins. The diagonal indicates agreement. This plot and the Brier score assess calibration; neither proves calibration for real dealership customers. We do not calibrate or retune using this holdout.

8.1 Measured training evidence¶

The evidence keeps two fits distinct. For the checked-in artifacts inspected on October 27, 2026:

  • Saved application model: fitted earlier on training plus validation (85%). Its stored estimator records 47 iterations. Original timing and warning observations were not saved, so those values remain unknown.

def evidence_sha256(path):
    digest = hashlib.sha256()
    with Path(path).open("rb") as stream:
        for chunk in iter(lambda: stream.read(1024 * 1024), b""):
            digest.update(chunk)
    return digest.hexdigest()

def matching_training_evidence(report):
    try:
        provenance = report["provenance"]
        required = {
            "model_bundle.joblib": ROOT / "models/model_bundle.joblib",
            "model_metadata.json": ROOT / "models/model_metadata.json",
        }

            if evidence_sha256(path) != provenance["application_artifact_sha256"][name]:
                return False

        return isinstance(report["loss_history"], dict)

9. How the Streamlit app uses this work¶

  1. Upload an unlabeled CSV containing id and the 13 input fields. The supplied demo is a safe starting point; its rows have no target labels.
  2. The app checks the input schema, required values, category membership, numeric domains, and identifiers before scoring.
  3. Choose the number of customers K that can be contacted.
  4. The saved pipeline computes Yes-label scores. The app sorts scores from highest to lowest and uses the same reproducible ID tie rule.
  5. Review the top K and download the ranked results for a proposed outreach list. Actual outcomes would need to be collected before measuring real customer performance.

The app is a class-project decision-support prototype. It does not contact customers automatically, verify their purchase intent, or make eligibility decisions. Real deployment would require a lawful and appropriate data collection process, subgroup review, and validation on real labeled profiles.

Monitoring plan: check invalid inputs and scoring failures, observe changes in feature and score distributions, and reevaluate ranking and calibration when reliable new outcome labels become available. With this static synthetic dataset, live drift and business impact remain unmeasured.

10. Conclusions and limits to carry into the presentation¶

  • The validation comparison selects a candidate under a fixed contact-capacity assumption. Holdout results assess its final refit under that same rule.
  • Lift@K summarizes enrichment of supplied Yes labels. It is not a causal uplift estimate, additional sales count, or return-on-investment calculation.
  • No missing-value repair or outlier removal was needed in the initial audit; real customer uploads may have defects and should not be silently repaired.
  • Gender and other demographic fields are present. Predictive usefulness does not by itself justify operational use. Review subgroup outcomes and whether each field belongs in the intended outreach process before a real deployment. No fairness conclusion has been established here.
  • One fixed split, three modest candidates, and synthetic data limit the strength of conclusions. Future work can use cross-validation, external labeled data, and a confirmed outreach capacity without repeatedly tuning against the holdout used here.
